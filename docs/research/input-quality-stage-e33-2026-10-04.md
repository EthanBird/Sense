# E33：个人词库恢复的重复评分与空别名开销

## 结论与范围

本轮生产改动仅在 `MemoryUserLexicon`：

1. 淘汰最弱词条时，每个候选只计算一次分数，使用原始类型比较，去掉链式比较器的重复评分和装箱。
2. 当前及历史别名均为空时直接返回空集合，跳过两套空的规范化、去重、排序流水线。

保留原评分公式、衰减、容量、时钟采样、同分规则和数据库格式；不调整候选权重，不更换模型或词库。
编译后的基线、首版及最终版 APK 的 25 项 `assets/` 内容摘要完全相同。
此次只提交开发分支，线上 v0.4.16-rc.3 及其正式签名 APK 保持不变。

## 从 E32 观察到具体热点

E32 的“选择输入法到观察模型就绪”含系统切换、全部资源装载和轮询，并非 SQLite 独占耗时。
源码确认 `PersistentUserLexicon` 在 `sense-decoder-loader` 后台装载，不是主线程同步读库。
按三个假设分解：饱和别名/简拼索引重复排名、上下文解析与对象创建、SQLite 读取。

专用 API 37 x86_64 模拟器中，通过 DexClassLoader 加载 rc.3 原 Debug APK，
实际调用其 `UserLexiconDatabase.loadAll()` 和 `MemoryUserLexicon` 构造函数。
测试在独立 fixture UID 中执行，只替换 fixture 自己的数据库，不借用 Sense 用户数据。

初次诊断中，一万词有共同别名 `qqq` 的索引构造约 1,365 ms；
只移除这个共同别名后约 179 ms。两者受执行顺序/JIT 影响，不把比值当作最终优化收益。
另一次侵入式 ART 采样中，构造根区间观测 CPU 1,489,055 μs：

- `addBoundedIndexEntry` inclusive 82.2%；
- `weakestKey` inclusive 81.6%；
- `PersonalizationScoring.rankingBoost` inclusive 47.2%；
- `UserContextSelection.sanitize` inclusive 3.9%。

inclusive 区间重叠，不相加。装箱、比较器和评分是具体修改点；这些采样不是自然启动耗时。
共同别名属于刻意制造的 128 槽饱和压力，不代表普通用户别名分布。

## 语义回归先于修改

新增 `PersonalDictionaryEvictionTest`，共 5 项：

- 固定种子的 1,000 组子集与原链式比较器逐项比较，包含重复 key、缺失记录、空集、异常持久化证据；
- 分数、时间、文本的并列规则，以及完全相同排名时保留最先遇到的淘汰对象；每次淘汰仍只读取一次时钟；
- 简拼/别名 128 槽饱和时，所有全拼记录仍可查，不因索引压力删除持久化词条；
- 全拼同码及全局容量淘汰的对象、回调次序和各索引清理与原规则一致；
- 无别名恢复、后续新增/保留别名和不同词条之间的集合独立性。

前四项先在原实现通过，第五项先在尚未增加空集合快路的首版通过；然后验证最终实现。
这是等价性测试，不声称原实现的功能断言曾失败；性能问题由独立 Android 对照证明。
`Float.compare` 保留原 Float 比较语义，时间按升序、文本按降序，完整并列保留遍历先后。

## 固定 Android ABBA 对照

工具：`tools/measure_personal_store_android.py`。
同一模拟器、原 APK 字节码、同一批 SQLite 字节、固定时钟；四块顺序为原版/候选/候选/原版。
每块新 fixture 进程；三种数据各一次预热，随后固定五轮。
总计 72 次构造，其中预热 12 次；每版本每数据集 10 次计时。
构造计时之外，对所有记录字段、索引成员及集合迭代顺序、码长计数和最后分配时间计算摘要；
顶层映射按键规范化。各数据集在原版与候选间摘要一致。

预先冻结的门槛：三组恢复 wall/CPU 中位数及观测 P95 均不回退；
一万词饱和别名组 wall 中位数至少降低 15%。不通过时保留整组，不靠重复同一产物挑选结果。
P95 每组仅 10 个样本，实际上取到该组最大值；不代表总体尾延迟或统计显著性。

### 首版：保留失败

仅替换淘汰扫描后，一万词饱和别名组中位数 1006.70 → 481.62 ms，
但无共同别名对照组 100.94 → 103.78 ms，严格不回退门槛失败。
此微小差异本身不证明实际回退原因；首版没有被宣布验收通过。
检查无别名路径后，第二版增加明确的空集合快路，而非重跑同一实现。
首版源码、补丁、APK 摘要和四块原始观测全部保留。

### 最终版：相同门槛通过

以下仅为**内存索引构造 wall 耗时**，不含 SQLite 读取：

| 数据集 | 原版中位数 | 最终版中位数 | 原版观测 P95 | 最终版观测 P95 |
|---|---:|---:|---:|---:|
| 1,000 词，共同别名 | 120.90 ms | 47.70 ms | 132.75 ms | 60.60 ms |
| 10,000 词，共同别名 | 1010.02 ms | 482.53 ms | 1086.21 ms | 535.22 ms |
| 10,000 词，无共同别名 | 97.64 ms | 82.45 ms | 132.93 ms | 111.40 ms |

CPU 中位数分别 98.60 → 44.27、948.08 → 462.95、89.54 → 75.66 ms；CPU P95 也均下降。
一万词压力组的构造 wall 中位数降低约 52.2%。SQLite 单独测量并保留，不宣称读取本身被优化。
不把这张表当成键盘首帧、每键延迟或手机实测。

## 构建、实际输入和交付

最终 Debug APK：`404ababaee1b040b9192c3ae08f3e238563cb75b506aecc04aa58b9f04e85b0e`。
参照 rc.3 Debug APK：`2d0f42c1bd6944b1a2fff1ab296d3065d6fbd3e75dceea9624fd6fa060010da1`。

948 项主机测试通过：core-input 396、ime-service 317、ime-ui 235。
Python 执行 448 项，447 通过、1 项既有 Windows 符号链接权限测试跳过。
构建与工具测试完成后才开始性能测量，避免同时跑 Gradle 或整套主机测试干扰。

最终产物另完成 E32 同样的四块真实 IME 容量回归：56 次外部编辑框确认、4 次不同 PID 重启，
程彻/智能体等七个抽样词的重复接受计数持久化，全表行身份与上下文映射保留，无关词条未变。
1,000 / 10,000 词的短词确认中位数分别为 69.5 / 72 ms，P95 为 138 / 148 ms。
选择 IME 到观察模型就绪分别为 3,409/3,301 ms 和 4,428/4,614 ms。
这是单产物功能/容量回归，与 E32 非同批次配对，不作为按键加速证据；
例如一万词这组确认 P95 高于 E32 的 126 ms，没有据此宣称每键延迟也降低了 52%。

另外在同一最终 APK 上重新执行 24 项系统输入场景：普通外部编辑框 10、学习/持久化 6、
上下文选择 8，全部通过。每组核对已安装 APK 摘要；未把历史测试累计成这次的新执行数。

系统输入回归及证据索引见 `benchmarks/results/e33-acceptance-gate.json`；
原始成功、失败观测及对应源码均由 `e33-evidence-manifest.json` 引用。

仍未覆盖真实手机、多厂商系统以及输入法 UI 上新增词触顶的完整淘汰体验；
当前优化不解决自然整句同音歧义或之前被拒绝的跨音节纠错开销。
这些继续属于质量专项，不据本轮构造加速宣称整体目标完成。

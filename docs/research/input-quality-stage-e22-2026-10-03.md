# E22：区分完整解码成本、首次调用与系统触摸测量

日期：2026-10-03。继续优先优化 26 键全拼；本轮只修改独立 Android 测试宿主和评测工具。
Sense 生产代码、搜索预算、词库、模型以及待评估 APK 均保持 E21，不把换测试方式当作产品提速。

## 为什么先纠正测量

E21 的词尾补全和显式别名学习修复通过功能回归，但两轮系统 ABBA 都未通过既定延迟门槛。
已有 ART 采样中，新增评分方法占候选版解码采样 CPU 约 1.08%，更多时间在组句和纠错路径；
各版任务数、取消历史并不一致，所以这不足以定位性能差异。

本轮在运行前固定三个待检验解释：完整解码自身变贵、首次执行状态不同、触摸节奏导致不同取消/预热历史。
保留 E21 原失败门槛，并让三个因素分别有记录，而非继续增加缓存或缩小候选预算。

## 1. 从冻结 APK 加载实际 Android 字节码

新增 `FrozenApkEngineTest`。它属于独立外部编辑器测试模块，不随 Sense 发布：

- 校验 E20/E21 APK SHA-256，再通过独立 `DexClassLoader` 加载各自实际 core 与 Kotlin 类。
- 校验类加载器隔离，逐项使用 APK 内的词库、syllables、bigram、英文词库和 SCNG 模型。
- LM 权重 0.5、OOV −4、limit 255、空上下文、空用户词库，不学习、不取消任务。
- 四个新仪器进程按参考/候选/候选/参考执行；每进程十组输入正反顺序交替，共六轮。
- 只在完整 `decodeProgressively` 调用两侧测 wall time 和当前线程 CPU；装载、序列化与哈希在计时之外。
- 保存完整 progressive 结果指纹，检查每次重放和各进程之间的一致性，而不只比较第一候选。

遵循 Android 14 的动态代码加载要求，在已打开的写入文件描述符上设置只读后复制，再校验 SHA。
相关接口与要求见 [Android DCL 文档](https://developer.android.com/about/versions/14/behavior-changes-14#safer-dynamic-code-loading)
和 [DexClassLoader 文档](https://developer.android.com/reference/dalvik/system/DexClassLoader)。

首次仪器运行因反射构造器将 `Collection` 写成 `List` 而失败，没有产生计时样本。
失败目录和原源码保留；修复宿主后使用新目录，不覆写原失败。

### 240 次固定完整调用的结果

| 阶段 / 每版样本数 | E20 wall 中位数 / P95 | E21 wall 中位数 / P95 | E20 CPU 中位数 | E21 CPU 中位数 |
|---|---:|---:|---:|---:|
| 每进程第一轮 / 20 | 226.81 / 530.45 ms | 264.25 / 610.46 ms | 217.43 ms | 248.23 ms |
| 随后五轮 / 100 | 145.84 / 369.69 ms | 116.66 / 280.60 ms | 133.97 ms | 106.84 ms |

十组输入全部完成；八组既有完整输入的全部候选结果在两版间一致。
`nime`、`renme` 保留 E21 预期的“你的→你们”“人的→人们”变化。
“今天有一点类”的既有语义错误仍保留，不拿它当准确率正确标签。

**解释边界**：该路径未复现持续的热解码退步，但第一轮候选版更慢。
这不证明 JIT 是根因；测试宿主、类加载器、查询顺序、任务取消与实际输入法不同。
第一轮也不等于每条输入都处于冷状态。以上结果不替代 E21 的系统延迟门槛。

## 2. 修正外部编辑器的唤起时序

第一次系统诊断四个区块中，前三个在 `@Before` 阶段失败：第一块外部编辑框已经显示，但 Sense 键盘没有出现；
第二、第三块失败于等待 production runtime 就绪。这三块均未产生确认计时。第四个参考区块完成 16 次确认。
这些失败保留，不组成有效 ABBA 性能比较，也不把不同的准备失败合并归因成焦点问题。

日志记录了 `PHASE_CLIENT_VIEW_SERVED` / `PHASE_SERVER_UPDATE_CLIENT_VISIBILITY`，没有应用崩溃记录。
旧宿主在 `onCreate` 后固定延迟 250 ms 请求键盘；这个计时并不保证窗口已获得焦点。
按 [Android 键盘可见性说明](https://developer.android.com/develop/ui/views/touch-and-input/keyboard-input/visibility)，
改成窗口获得焦点之后再 post 一次请求，每个 Activity 只请求一次，避免用户主动收起后又被自动打开。

只改变这个宿主变量、保留原触摸注入与清理过程，三次清空专用模拟器调试数据后的启动/实际选词均通过。
这支持针对“键盘未出现”的焦点时序修正，但不解决另两次运行时就绪超时，也不声称所有 Android 版本与窗口状态已覆盖。

## 3. 标称按键间隔不等于实际按键间隔

重新检查 E21 cadence 文件：调用后等待 12 ms 的测试，实际按键起点间隔常为 100～700 ms。
所以原测试覆盖的是实际触摸上屏和任务顺序，并不是已证明的 12 ms 高速连续输入。

新诊断在外部编辑框主线程记录第一次出现预期文字的时刻，另行断言最终内容和 composing 状态，
避免把轮询发现时刻当作精确的上屏时刻。每次按键都保存实际起点间隔。

将公开 `injectInputEvent(event, false)` 设为异步后，实际间隔仍明显高于目标 32 ms。
AOSP 表明该重载仍固定等待窗口动画/Surface 事务。测试中随后使用三参数测试 API，
明确设置 `sync=false`、`waitForAnimations=false`，不修改系统隐藏 API 策略或全局动画设置；其他测试维持旧默认注入方式。
参见 [UiAutomation 实现](https://android.googlesource.com/platform/frameworks/base/+/a3894f99a570/core/java/android/app/UiAutomation.java)。

单次可用性检查的 16 次上屏全部正确，但 350 个按键间隔中位数仍为 121 ms、最大 329 ms。
这次试验没有达到 32 ms；三参数测试 API 仍经由 WindowManager 的事务后注入入口，
见 [UiAutomationConnection 实现](https://android.googlesource.com/platform/frameworks/base/+/a3894f99a570/core/java/android/app/UiAutomationConnection.java)。
这是接下来分离注入/调度成本的线索，不单凭源码断言实际延迟全部来自该入口。

### 四区块诊断仍不构成有效性能对照

| 区块 | 版本 | 确认结果 | 实际按键间隔中位数 / P95 |
|---|---|---:|---:|
| 1 | E20 | 16 / 16 正确 | 136 / 279 ms |
| 2 | E21 | 16 / 16 正确 | 131 / 221 ms |
| 3 | E21 | 16 / 16 正确 | 120 / 225 ms |
| 4 | E20 | 准备阶段失败，无计时样本 | — |

第四区块的键盘已成功显示，截图也证实这一点；失败是等待 production runtime 就绪超过原有 20 秒期限，
不是再次“没有键盘”。日志中可见类验证耗时、Surface 事务超时、跳帧，以及随后 Character/Association 模型 READY。
这些现象提示准备阶段存在明显延迟，但尚未单独定位加载、调度和渲染成本。

**没有补跑第四区块凑成成功对照，也没有延长期限抹掉失败。** 汇总工具保留三个成功区块及一个失败区块，
`confirmationMs` 为 null，禁止把不平衡成功子集汇总成两版性能结论。实际按键间隔仍不支持 32 ms 快打覆盖。

新增工具回归同时验证：缺少区块、重复/缺失 cadence、时间戳不匹配、错误上屏和失败区块均不会变成有效性能比较。

## 4. 为下一项召回修复收集最小事实

只读扫描当前实际 SPLX 资产，确认 `beiji` 不是“词库没有北京”：

- 共有 838 个 `beiji` 开头的 canonical 键；`beijing` 在这段范围的第 **130** 个。
- 当前普通前缀扫描只读取前 **96** 个键，额外分支只覆盖单音节键。
- `beijing` 条目确有“背景 / 北京 / 北境 / 倍镜”，其中“北京”的权重为 22,789、tier 0。
- 统计前缀索引最长只有 **4** 个字母，存在 `{beij`，不存在 `{beiji` 或 `{beijin`。
- E21 已保存实际完整候选与评分池均缺“北京”的记录。

这把排查范围收敛到**有界前缀召回漏掉字典已有词**；还需用跨越扫描边界的最小字典测试验证修复，
不通过为“北京”硬编码加分或直接扩大全部查询扫描预算来掩盖问题。
“北极”作为 `beiji` 的完整拼写首选仍合理，目标是让常用补全保持可选，而非消灭歧义。

## 决策

- E21 功能改进留在开发分支；其性能推广门槛仍未通过。没有本轮生产提速声明。
- 未获得可靠的 32 ms 实际触摸覆盖，后续需要先测注入分段成本或采用独立、可验证的快速事件源。
- 完整解码首次/重复调用分开评测，不把实验宿主的热吞吐改进外推成用户感受到的延迟改善。
- 保留已发现的 `beiji` 缺“北京”、类/累等质量缺口。后续优先做有最小复现的召回和执行成本修复，
  不为通过计时而减少搜索预算，不持续重复同一基准挑选有利结果。
- 全程只使用专用模拟器；未改动用户手机，未使用正式证书，未上传或发布。

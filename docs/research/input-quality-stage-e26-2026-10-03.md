# E26：语言模型字符查找优化试验，未进入默认实现

## 决策

只读 BMP 位表保持了全部已检查的模型分数和候选结果，且仅增加 8 KiB 常驻内存；
但真实快打 ABBA 的确认中位数变慢，未通过运行前固定的双指标门槛。
因此**恢复原生产实现**，保留试验源码、APK 哈希、原始数据及扩大后的回归测试。
没有覆盖已发布的 `v0.4.16-rc.1`，没有把局部尾部改善宣传为产品全面提速。

| 同一轮 ABBA | 确认数 | 中位数 | 观测 P95 | 最大值 |
|---|---:|---:|---:|---:|
| E23 既有开发版 | 32 | 134.5 ms | 326 ms | 353 ms |
| BMP 位表试验版 | 32 | 145 ms | 300 ms | 313 ms |

64 次确认、8 次立即续打、全部原始拼音前缀检查通过。
四组实测按键间隔中位数 33 ms、P95 35～36 ms；固定规则要求中位数和 P95 均不高于基线，
本轮中位数检查为 false。未重跑以选择有利结果。

## 为何选择这个试验

对 E25 已有 trace 作事后时间关联：每次确认在最后字母之后、外部文字出现之前，
均有且仅有一个完成的 `Sense.Pinyin.decode` 片段。该片段结束到外部文本回调的差值
中位数 2.262 ms、P95 5.114 ms、最大 6.302 ms（64 次）。
trace 没有任务 ID，这只是时间关联，不冒称函数级因果剖析；它支持优先检查解码而非额外增加 UI 等待。

已有 E21 ART 采样记录中，数组二分查找占据明显采样时间。源码显示每次模型转移会对
两个上下文字符和后继字符重复检查词表，发射前的 `containsCodePoint` 又进行一次检查。
试验仅把 256 项以上词表的 BMP 存在性查询改为固定 1,024 个 Long 的只读位表，
补充平面、BOS/EOS/UNK、概率计算、回退算式及所有候选搜索预算保持原样。
这不是新训练模型，也不是新增用户文本缓存。

## 结果等价与内存

- 在两个独立类加载器中加载修改前后的固定 core JAR，使用同一生产 SCNG：
  1,114,116 次字符存在性查询、3,352 个 unigram 查询、236,527 次转移逐位一致。
  转移覆盖文件中全部 bigram、trigram 记录及固定随机种子的 20,000 次回退查询。
- 生产模型数组负载估计 3,090,904 → 3,099,096 字节；增加恰好 8,192 字节，不含对象头。
- 1,790 次既有 M14 progressive 重放的完整结果指纹全部相同，含 whole/prefix 候选顺序、
  canonical 拼写、来源与分数；词库、模型和输入数据 SHA 相同。
  主机中位数 7.089 → 6.635 ms 只作为主机诊断，不替代 Android 上屏测量。
- 新增大词表测试覆盖所有 Unicode 范围、位边界、代理区、补充平面和哨兵；多线程概率逐位一致。
  初始测试的唯一失败是“旧实现未分配新增位表”的精确内存断言，不是输入错误。
  恢复后保留不强制实现方式的内存上限与语义回归。

## 真实快打条件与全部观察

一次固定旧/新/新/旧执行，2026-10-03 14:13:32～14:16:07 UTC。
同一 API 37 x86_64 AVD、E24 shell helper、现有 20 秒 runtime-ready 条件，清空的只有专用 AVD 的 Debug 数据。
禁止个性化学习；每组 8 条输入正序、倒序，然后两条立即续打。
本轮沿用 E25 workload，不是新的盲测或用户手机测试。

主机候选等价重放和一次短模型对照在系统测量期间也执行过，宿主 CPU 并非完全隔离；
因此时延差异仅是本轮观测，既不据此断言位表必然变慢，也不据尾部降低声称因果提速。

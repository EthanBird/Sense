# E40：把逐键响应、确认等待与实际绘制帧分开测量

## 本轮结果

本轮回到真实输入法 UI，不继续追加 E39 模型参数试验。
新增独立外部编辑器仪器场景与严格 HWUI 帧收集/审计工具，在原 E34 Debug APK 上完成：

- **6 次真实快打确认 + 2 次展开滑动后点选**全部正确；118 个原始拼音前缀逐字、按序送达外部编辑框。
- 快打产生 190 个普通帧，展开滚动产生 79 个普通帧；8 个窗口均无环形缓冲截断、无非零 Flags 帧。
- 逐键到外部 composing 前缀回调的中位数 **20 ms**、P95 **45 ms**、最大 **62 ms**。
- 绘制主线程工作中位数约 1.4 ms；主要较长部分位于 RenderThread/图形完成等待区间。
- 运行环境明确为 **API 37、1080×1920、420 dpi、字体 1.0、无窗口 SwiftShader 软件图形后端**。
  这解释了为何不应直接把模拟器图形完成时间视作手机体验或全部算到候选算法头上；尚未做后端消融证明因果。

新增的是可重复的 UI 诊断与回归覆盖，**未修改生产算法、绘制代码或 APK**；
没有证据宣称本轮使输入更快，也未发现这组场景的丢键、错交、候选滚动选错或几何跳动。

## 为什么另做这组测量

已有 E34 的 129.5 ms 中位数、296 ms P95 是固定工作负载中“空格事件→外部文本确认”的时间，
包含当前查询搜索、调度与编辑框提交，不是帧时间，也不是每次字母键都要等这么久。
E40 同时保留三个独立时间轴，避免拿其中一个替代其他指标：

1. **逐键接收**：shell 触摸开始至外部 `TextWatcher` 收到该原始拼音前缀；包括按下/抬起的 8 ms 间隔。
2. **确认等待**：空格触摸开始至外部编辑框首次出现完整确认文本。
3. **HWUI 帧完成**：实际 `:ime` 进程中 InputMethod 窗口的 `FrameCompleted - IntendedVsync`。

Android 官方提供 `dumpsys gfxinfo ... framestats` 的帧诊断入口；
[dumpsys 文档](https://developer.android.com/tools/dumpsys#gfxinfo)与
[AOSP FrameInfo 定义](https://android.googlesource.com/platform/frameworks/base/+/master/libs/hwui/FrameInfo.h)
用于核对字段意义。工具按实际列名解析，不把某一 Android 版本的固定列号写死。
`FrameCompleted` 不是设备屏幕真正显示像素的保证，本轮数据的 `DisplayPresentTime` 也未用于这种推断。

固定产品 APK SHA-256：`1dfa19d48e9fcfdb491f9bed56c24911192caebe3ce8e7f42c65d1b67895a9df`。

主机入口校验专用 `sense-input-quality` AVD、`emulator-5580`、已安装产品 APK、触摸 helper 和
测试 APK 摘要，确认未启用 debug wait。只清除这个一次性 AVD 的 Sense Debug 数据，未操作实体手机。
系统 IME 和硬键盘显示偏好由 fixture 恢复，主机额外确认最终回到 Gboard、debug_app 为 null。

运行时就绪后，在同一 IME PID 内执行正序/逆序各一轮：

- `nihao → 你好`
- `woxihuanbeijing → 我喜欢北京`
- `tangmumeiyouzhuyidaomalihuanlexinfaxing → 汤姆没有注意到玛丽换了新发型`
- 输入 `shi`，展开 255 个候选，连续滑动，点击真实可见候选，并核对外部提交文本恰好等于被点击词。

每个窗口之前重置 gfxinfo 统计，结束后短暂等待已提交工作完成，再读取同一进程/窗口的帧流。
未开启 CPU 方法采样，没有在输入过程中调用 dumpsys。测试时 `noLearning=true`，不把重复输入的学习收益当成性能改善。
触摸目标间隔 32 ms，实际 118 个间隔中位数 33 ms、P95 37 ms、最大 40 ms。

## 实际观察

### 用户输入接收与确认

| 指标 | 数量 | 中位数 | P95 | 最大值 |
|---|---:|---:|---:|---:|
| 字母触摸→原始前缀回调 | 118 | 20 ms | 45 ms | 62 ms |
| 空格触摸→完整确认回调 | 6 | 178.5 ms | 346 ms | 346 ms |

六次确认按执行顺序为 125、346、302、232、112、38 ms。样本较少，P95 就落在最大值，
并且查询集合/启动状态与 E34 ABBA 不同；**不据此判断 rc.4 相对 E34 退步或提升**。
首轮和后续确认差异明显，最新查询搜索、首次调用/JIT/缓存成本仍值得单独诊断。

### 实际 IME 帧

| 时间段 | 快打中位数 / P95 | 展开滚动中位数 / P95 |
|---|---:|---:|
| HWUI 总完成 | 34.10 /50.83 ms | 17.97 /19.70 ms |
| Vsync→主线程开始 | 2.34 /12.56 ms | 1.64 /2.60 ms |
| 主线程开始→提交 RenderThread | 1.43 /6.92 ms | 1.37 /2.46 ms |
| DrawStart→SyncQueued | 1.10 /6.56 ms | .72 /1.30 ms |
| RenderThread 队列等待 | .62 /13.65 ms | .23 /2.41 ms |
| 发绘制命令→帧完成 | 20.90 /31.65 ms | 14.61 /16.93 ms |

主线程工作最大 11.74 ms（快打）/2.50 ms（展开）。这组数据没有复现百毫秒的主线程绘制停顿。
统计的是时间跨度，部分异步阶段可能重叠；总帧分位数直接从原始总跨度计算，各分段分位数仅独立解释。
按每行报告的 FrameDeadline 统计，快打 76/190、展开 18/79 晚于该值；
它不是对 Android JankTracker 所有判断规则的复刻，更不代表自然手机“掉帧率”。

每个窗口 9～61 帧，全部低于 120 环形缓冲容量。进程总数、窗口总数和原始行数逐窗口相同；
全部 269 帧均位于对应窗口内，无非零 Flags、重复行、未完成哨兵或反向时间戳。
帧之间相关，190 帧不是 190 次独立键入实验。

人工查看实际展开截图，确认滚动后的候选文字完整、顶部 composing 与底部数量区分离；
仪器测试确认滑动后点选提交准确、键盘边界不变。这仅覆盖该屏幕配置，不冒称多厂商视觉验收完成。

## 下一步判断

优先进一步分解最新查询自身的搜索和首次调用成本，而不是凭模拟器的软件图形完成时间贸然删减 UI。
候选输入质量、逐键增量复用和更广 Android/厂商设备覆盖仍未完成；本轮只补齐了此前明确缺少的
**实际 IME 帧基线**，不把这个局部验收当作整个输入质量目标完成。

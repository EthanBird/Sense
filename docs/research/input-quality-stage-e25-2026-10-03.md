# E25：真实快打下的确认与连续续打

## 结论

同一专用 API 37 x86_64 模拟器、同一事件源、固定 ABBA 一次运行全部完成。
64 次逐键确认及 8 次“立即确认后继续输入”均得到预期文本、结束 composing；
全部 64 次确认前的原始拼音前缀按顺序出现在外部编辑器中。
每组实测按键间隔中位数 33 ms、P95 35～36 ms，目标 32 ms 的快打覆盖成立。

| APK | 确认数 | Space 到首个预期文本中位数 | 观测 P95 | 最大值 |
|---|---:|---:|---:|---:|
| E20 旧基线 | 32 | 147.5 ms | 316 ms | 331 ms |
| E23 当前开发版 | 32 | 144.5 ms | 317 ms | 321 ms |

当前开发版没有显示明显提速。预先锁定的“中位数与 P95 都不劣于基线”规则因
P95 高出 1 ms **未通过**；不根据结果放宽规则，不重复挑选有利轮次。
1 ms 差异也不足以证明产品出现真实回退，本实验不是统计显著性检验。
本轮没有生产代码、词库、模型或发布 APK 的修改。

## 执行条件与边界

- 产品：E20 `424d96c9ec01c44bda3db650cd0ab24543fbe9031a794698c2bdf14c8a5de21f`；
  E23 `7ce9874adf9f9b0a84408aa67c90727b8d98ab5f4e7f1433e1d4eded05ee16ed`。
- 事件源：E24 已验证的独立 adb-shell DEX，SHA-256
  `c43716637ff8e3df199ec668e86c0b7c3b4fc85bab9760ca291b8699bafc1de9`。
  它不进入产品 APK；真实触摸通过系统送到 IME，而非直接调用解码器。
- ABBA 顺序为旧、新、新、旧。每组安装固定 APK、清空**专用模拟器的 Sense Debug** 数据，
  维持原有 20 秒 runtime-ready 条件，不增加人工热身；编辑器禁止个性化学习。
- 8 条既有短中长查询各执行正序、倒序一遍；两条长查询分别紧接 ` nihao `，中间不等待解码。
- 运行前锁定输入、APK、helper、生产源码、规则；运行时记录测试源码与安装后 APK 哈希。
  开始 `2026-10-03T13:55:14Z`，结束 `13:57:49Z`，仅一次完整运行，无准备失败或重跑。
- 时间来自按键注入起点与外部 EditText 的 TextWatcher。不是屏幕绘制时间；排除初始资源加载。
  同一 APK 的首次/再次查询有缓存、ART 和预热差异，未将这些因素分别归因。
- `jintianyouyidianlei → 今天有一点类` 是已知错误输出的行为保持检查，不算语言准确率正确答案。
- 本轮只比较以上两份 Debug APK；没有对正式签名 Release APK或实体手机做性能认证。
  不将 E21/E22 不同启动和注入条件下的较大时延与此轮作提速比较。

## 全部逐查询观察

每格依次保留两个组内的正序、倒序观测，不删慢值；单位 ms。

| 输入 | 旧基线 | 当前开发版 |
|---|---|---|
| nihao | 130, 33, 119, 36 | 108, 19, 117, 36 |
| woxihuanbeijing | 316, 91, 331, 99 | 321, 106, 317, 111 |
| qingfageweizhigeiwo | 164, 102, 185, 88 | 167, 99, 147, 85 |
| qingjianchayixiayoujian | 207, 159, 189, 132 | 205, 153, 188, 147 |
| zhegeyingyonghenhaoyong | 158, 111, 114, 103 | 139, 108, 132, 121 |
| jintianyouyidianlei | 128, 135, 137, 133 | 138, 93, 142, 106 |
| tangmuhemalimeitianwanshangdoukandianshi | 228, 214, 225, 180 | 199, 210, 224, 203 |
| tangmumeiyouzhuyidaomalihuanlexinfaxing | 244, 215, 222, 223 | 226, 233, 239, 243 |

“我喜欢北京”首次约 320 ms，再次约 110 ms，是下一步优先定位的明确现象；
更长输入并不总是更慢，所以不以长度阈值削减搜索。
四组 trace 均完整：取消 decode 数依次为 353、356、347、345，完成数为 81、77、79、87。
完成片段包含逐键过程中的短前缀，不当成 64 次最终确认的同义指标。

下一次诊断的可证伪假设（优先级从高到低）：
1. 未缓存词边/纠错图导致首次较慢：固定 ART 状态后，独立清理解码缓存应恢复较高成本。
2. ART 编译/类初始化导致较慢：保留缓存状态而改变运行时预热，应改变热点分布及耗时。
3. 主线程发布/确认等待占较多时间：最后一次完整 decode 已结束到编辑器收到文本之间应出现较大间隙。
先用现有 trace 和有界采样区分，再选择生产改动；不为个别查询加词频特判。

# E29：显式改选的短上下文记忆

## 已实现的用户行为

26 键全拼现在分别记住同一拼音在不同短上下文中的明确选择。例如用户选择：

- “人民”后 `quanli` → **权力**；
- “获得”后 `quanli` → **权利**。

后续相同上下文优先使用对应选择，而不是让全局使用次数将其中一个词推到所有语境。
没有新增配置页，也不需要额外操作；沿用现有候选点击、分段选择和确认流程。
这是一项个人适应能力，不是宣称静态词句模型已经解决所有同音歧义。

## 复现与定位

先给学习证据增加一个尚未使用的上下文字段，现有排序上的最小单测失败；
编译笔误的日志单独保留，不将它计为用户缺陷复现。
核查三个环节：记录是否携带上下文、排序是否读取上下文、缓存是否混用。
前两项原实现都缺失，单纯清缓存不会补出丢失的学习信息。

更重要的是：同一个 Android 测试 APK，在冻结的 E27 应用上也复现失败。
两次明确改选后，再输入“人民 + quanli”，旧包仍给“权利”首选，而非刚选择的“权力”。
修复包用**相同测试 APK**通过立即复用、Space 接受、真实 IME 进程重启与隐私字段隔离。
所以这不只是人工构造的核心接口测试。

## 实现规则与边界

1. `UserLearningEvidence` 携带提交前上下文。Service 在调用 InputConnection 前冻结它，
   避免同步选区回调清空 composing 状态后记错位置；分段选择记录各自被点击前的上下文。
2. 只保存连续汉字的最后两个 Unicode 码点；标点、空白、英文会切断边界。
   每个词最多保留 8 个上下文时间戳，不保存整段编辑器内容。
3. 只有明确候选点击、分段选择和由其组成的确认建立上下文偏好。
   普通 Space 默认接受继续累计原全局证据，但不创建或覆盖上下文选择。
4. 相同上下文和完整拼音/已明确学习的别名，使用最近一次明确选择；只匹配简拼不会触发此规则。
   在原候选来源评分域中以当前最高分 +0.5 提升该词一次，不将此展示分数写回使用证据。
5. 最近 30 天的明确选择参与上下文优先；过期后恢复原全局学习/模型排序，词条本身仍保留。
   单码点快速删除、整词立即替换会撤销对应上下文；手动降权清除该词全部上下文优先，忘记删除整条记录。
6. 拒绝反馈携带原选择的时间戳。旧编辑回调仍可记负反馈，但不会清掉随后发生的较新明确选择。
   另一个上下文的明确选择继续保留；没有汉字上文的快速拒绝也不清空其他上下文。
7. 存储和匹配都只在本地；原隐私/密码编辑器的学习门控保持。没有服务器请求或生产逐键日志。

这不是词格内部所有词边的在线语言模型训练，也不是跨整段语义的泛化；
作用范围是用户正在确认的全拼词/词组及其紧邻上下文。

## 持久化和兼容

SQLite 从 v3 升到 v4，仅为原 `user_phrase` 增加 `context_selections` 列，默认空字符串。
上下文与词条通过现有串行写队列、同一个 upsert 事务保存；没有新增主线程数据库读写。
内存查询仍使用原拼音/别名索引，先在有界命中集确定上下文优先词，再按 limit 截断。
因此 limit=1、12、255 都保留同一明确选择。

新增持久化测试覆盖 v1/v2/v3 升级：旧词、use_count、创建时间和别名保留，
新增上下文可写入并在关闭/重开后恢复。畸形/超长存储值、补充平面汉字、不可变快照和容量都有纯 Kotlin 测试。

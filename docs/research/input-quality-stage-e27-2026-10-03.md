# E27：查询内复用纠错候选选择，保留冷启动覆盖缺口

## 决策与交付范围

保留本轮查询内缓存，提交到 `codex/input-quality-v2`。固定快打工作负载的双指标门槛通过，
已有候选结果及个人学习回归保持；这不是整体输入质量完成，也不是全面 100 ms 承诺。
已发布的 `v0.4.16-rc.1` 保持原样，本轮开发改动尚未包含在该 APK 中。

本轮到此结束性能微调。下一优先级回到日常同音词句排序及候选改选体验，
冷加载确认路径的确定性覆盖作为独立待办保留，避免通过反复碰运气把失败测试变绿。

## 生产改动

`PinyinDecoder.readSpellingGraphCorrections` 在单次查询内共享有界 `QuerySelectionCache`：

- 键为不可变词边列表的**对象身份**、语言模型状态、选择宽度及外部上下文。
- 仅复用无个人词覆盖、无强制拼音边界交叉的基础词边选择；个人词继续逐次合并。
- Scout 与完整 beam 的宽度分别入键；词频、LM 算式、纠错先验、候选和搜索预算保持原样。
- 路径自身的边界分数、文本、累计分数仍逐路径计算，没有复用整条历史路径。
- LRU 上限 128 项、4,096 个输入值和 4,096 个输出值；共享输入按每个键保守计费。
  返回不可变列表快照，支持协作取消；查询结束即释放，不跨会话保留用户文本。

三个新增单元测试覆盖身份/状态/宽度/上下文隔离、快照不可变、三种容量限制、
超大项绕过、计算异常、取消及不同查询隔离。最初的 red 日志是缺少新类的编译失败，
不是把一个已经复现的用户故障包装成测试。

## 选择该优化的依据

专用 API 37 x86_64 模拟器上，先输入 `nihao`，再首次和重复输入 `woxihuanbeijing`，
由固定 SHA 的 shell helper 按 32 ms 目标节奏生成系统触摸。ART 1,000 us 双时钟采样中，
`composePaths` 占解码采样 CPU 的 76.0% / 61.1%，纠错入口占 35.8% / 42.6%，
`language.extend` 占 26.3% / 19.5%。这些是重叠的 inclusive 比例，不相加。

采样含被取消的前缀和最终查询，并非只测最后一次解码；采样本身有扰动，
这里只用于定位重复计算，绝不作为正常输入延迟。工具和测试只存在于独立 fixture，
没有向发布应用加入调试入口。E26 被拒绝的 BMP 位表优化没有重新启用。

## 结果一致性和构建

- 修改前、后 JAR 独立重放 895 个普通状态、945 个开发错拼状态及 1,874 个测试错拼状态，各两遍。
  **7,428 次完整结果指纹全部一致**，包括顺序、来源、拼写和浮点分数。
  这是既有样本回归，不是新盲测，也不是准确率提升。
- M14 输出的 `sources` 字段读的是当前工作区；旧 JAR 的源码对应关系以 `before-lock.json`
  为准。新旧 JAR 单独固定 SHA，报告没有把当前源码元数据冒充旧 JAR 来源。
- 两版 APK 的 25 项 assets 逐字节一致；词库、字符 LM 和联想模型未变。
- core 383、service 312、UI 235，共 **930 项主机测试通过**；部分未变任务复用 Gradle 缓存。
  工具测试运行 430 项，429 通过、1 项既有权限测试跳过。
- Debug APK 构建成功，SHA-256：
  `a8c404702653196fc90a45f4197e02f4c7188569df7274c83604851d89d85ce7`。

## 一次固定 ABBA 系统输入对照

E23 / E27 / E27 / E23，8 条固定输入正序、倒序，每组再做两条立即续打；
64 次确认、8 次连续续打以及全部拼音前缀检查通过。实际按键间隔中位数均为 33 ms，
各组 P95 为 36 / 35 / 35 / 35 ms。没有重跑选好看的结果。
主机候选重放和 Python 套件均在该轮设备对照开始前结束。

| 确认延迟 | 样本数 | 中位数 | 观测 P95 | 最大值 |

| E23 | 32 | 147 ms | 299 ms | 327 ms |

中位数和观测 P95 均不高于同轮基线，通过运行前固定的局部门槛。

## 生命周期回归：通过项和覆盖缺口分开

- 学习组 4 项通过：真实候选选择、程彻/智能体复用、进程重启恢复及隐私隔离。
- 上下文组 8 项通过。
- 冷启动组运行 4 项：1 项通过，**3 项失败，保留完整日志和截图**。
  四项开始输入时均观测到 `ready=false generation=1`；同步 UiAutomation 输入实际
  42～91 ms/键，到空格确认前已变为 `ready=true generation=2 characterModel=READY`。
  三项失败均发生在“此刻仍应未加载”的覆盖前提断言，未进入后续确认断言。
  因此这不是已经观测到丢字，也不证明加载期间确认正确。

不删除上述断言，不延长计时器，不反复重跑选取通过结果，不拿普通慢解码测试替代冷加载证明。
确定性覆盖装载未完成时的确认/续打/换编辑框仍待单独实现。本轮没有动资源装载或确认队列代码。
专用模拟器原 Gboard 已恢复，没有操作用户手机。

# E41：重复字符评分的真实成本试验，保留原实现

## 结论

本轮从 E40 的首次确认长尾回到真实触摸路径，完成线程采样、一个固定优化、完整结果回放和一次 Android ABBA。
查询内字符评分复用确实减少模型调用，但整体确认中位数没有通过运行前写定的门槛。
**试验代码已恢复；不发布新 APK，不把 P95 的单项改善当作整体提速。**

| 同轮专用模拟器快打 | 样本 | 确认中位数 | 观测 P95 | 最大值 |
|---|---:|---:|---:|---:|
| E34 原 Debug | 32 | 134 ms | 314 ms | 348 ms |
| 字符评分复用试验 | 32 | 138.5 ms | 296 ms | 343 ms |

64 次确认、8 次连续续打、逐字前缀与四块发送节奏检查全部通过。
这是一轮固定已知负载的观测，不证明差异显著，更不代表所有 Android 手机。
没有修改验收阈值，没有重跑选择有利结果。

## 定位过程与假设

开始前向用户说明三个可检验方向：拼音图/词边计算、首次执行准备成本、主线程提交等待。
沿用外部编辑器与 shell TouchBurst，先完成 `nihao`，再分别采样首次及重复的 `woxihuanbeijing`。
目标为 `io.github.ethanbird.senseime.debug:ime` 中的 `sense-candidate-decoder`，
ART dual-clock / 1,000 µs 采样，原 Debug APK、事件 helper 均核对 SHA。

两次采样中的解码线程 CPU 区间为 1,435,739 / 838,122 µs；
`composePaths` inclusive 为 1,039,114 / 530,016 µs，
`PinyinLanguageScorer.extend` inclusive 为 300,576 / 187,934 µs，约 21% / 22%。
包含多个按键的被取消任务和最终任务，不是只采样最后查询；调用栈父子时间重叠，不应相加。
ART 显著扰动执行，因此这些值只定位热点，不拿来计算正常提速比例。
首次和重复的差异也不足以单独证明 JIT 是根因。

源码核对发现现有 `(state, word)` 缓存并不复用不同词边内的相同字符转移，
而一条转移可能进行多次词表及 n-gram 二分查找。选择这个明确的小范围假设做一次试验，
没有同时修改图搜索、beam、词频、候选数、模型或 UI。

## 固定候选与数值边界

运行前 `policy.json` 固定：1,024 个直接映射槽，Long key + Float value，共 12,288 字节原始数组负载，
对象头另计；按需初始化，每个 scorer 独立，解码结束即释放。
key 含完整两个上下文 token 和当前 Han 码点；碰撞只替换，绝不把另一 key 的值当命中。
原整词缓存保留；四元模型绕开此三元 memo。没有跨输入、跨用户或后台长期保留文本。
每字浮点相加顺序、未知字罚分、有限值处理、截断和词尾补全规则均保持。

先运行“整词与分词共用同一发射”的计数测试：旧实现 3 项中 1 项失败，
失败是多次执行相同概率查询，并非输出错误。候选版本通过该测试及碰撞/十万次替换检查。
另补 6,000 组含标点、补充平面汉字、未知字和非有限模型值的逐位控制，以及四元上下文隔离测试。
后两项是实现无关的数值回归，恢复生产代码后继续保留。

## 候选质量与实际调用量

首先重复 M15 的 945 开发回放、1,874 已知测试回放，以及 M20 两域各 128 状态：
所有非计时观察保持。M15 原报告只记录前五和召回/图探针等字段，**本身不证明完整列表等价**。
因此另外用 `EmissionMemoReplay.java` 在固定新旧 core JAR 上执行完整 progressive 输出指纹对照：
上述 3,075 状态加 8 个 Android 负载，共 **3,083 个完整结果全部一致**。
包括 whole/prefix 顺序、来源、canonical 拼写和 round-trip Float 分数；参考文本未传入解码决策。
这是旧语料回归，不是新盲测，也不是本轮提高输入准确率的证据。

该独立主机包装器还直接计数底层概率 API 调用，不用时间反推命中率：

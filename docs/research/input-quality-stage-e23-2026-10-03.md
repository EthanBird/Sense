# E23：有界扫描之后的末音节补全召回

日期：2026-10-03。主线仍为 26 键全拼，承接 E22 已确认的 `beiji` 召回缺口。
本轮修改 `PinyinDecoder` 与 `PinyinSyllableSegmenter`，词库、模型、评分权重、纠错图和整句 beam 上限保持。

## 复现与原因

“北京”在生产词库里，`beijing` 条目的 tier 为 0，频率权重为 22,789。
但 `beiji` 范围有 838 个 canonical 键，`beijing` 排在第 130；普通前缀扫描只取前 96 个，
统计前缀索引又只到四字母，因此常见词被字典序靠前的长词遮住。

先构造一个小 SPLX 词库：110 个有效拼音长码放在 `beijing` 之前，保留“北极”精确码、单字音节和“北京”完整码。
关闭纠错的真实解码路径仍缺“北京”，证明该问题不依赖纠错排序。
最初三个测试中两个失败：小词库越界召回、实际生产词库 `beiji` 召回；旧无 LM 与显式分隔控制通过。

独立 Android 编辑器也使用同一个测试 APK 对照：旧 E21 包四项中两项失败，均为 `beiji` 的“北京”缺失，
包括从 `beijing` 回删两个键后再选择的路径；空格提交“北极”和 Enter 提交 `beiji` 两项控制通过。
新 E23 包四项全过，“北京”是候选第二项，直接点选即可上屏，不用展开整页候选。

## 实现

仅在以下条件同时满足时补充查找：当前解码实际启用 LM、普通前缀范围确实超过 96 项、输入没有强制音节边界。

1. 以布尔 DP 求出已经输入部分的所有完整音节边界，不只使用贪心切分。
2. 尾部必须已经有字母，且前面至少有一个完整音节。只补足这个已开始的末音节。
3. 生成有限的完整码，通过已有二分查找精确探测；仅读取原扫描窗口之外的命中，避免重复处理。
4. 候选沿用原前缀长度惩罚、LM 特征、来源先验、每键候选数和最终候选上限；保留 canonical 拼音及 initials。
5. 无 LM/T9 的旧词库视图、个人新词触发的 LM 回退、显式 `bei'ji` 均保持原行为。
6. DP 与新精确查找循环继续检查协作取消，取消后没有部分结果写入跨查询缓存。

这不是把 96 项改成更大的扫描上限，也没有给“北京”或其他特定词加权。
新增成本是被截断查询上的一次音节 DP、有限精确查找及命中候选的评分；本轮不声称零成本或已提速。

### 一个测试预期的纠正

初版辅助方法测试错误地认为 `beijin` 只存在 `bei'jing`。
人工测试音节表同时含 `ji/na/nang`，因此 `bei'ji'n…` 也是已输入字母支持的边界，
生成 `beijina/beijinang` 合理。保留所有合法边界，纠正测试预期，没有为了单个答案删除歧义路径。
该次失败日志与原测试源码一并保留。

## 构建与当前边界

开发 APK 已构建，SHA-256 为 `7ce9874adf9f9b0a84408aa67c90727b8d98ab5f4e7f1433e1d4eded05ee16ed`，
87,092,864 字节。与 E21 相比仅 `classes7.dex` 内容变化，所有资产逐字节保持；使用 Android Debug 证书。

这一轮改善已存在字典词的可选性，不等于总体语言准确率提升，也未解决类/累等上下文歧义。
E21 系统延迟推广门槛仍未通过，E22 已明确原快打测试的实际节奏不足；本轮不会用主机耗时或新功能测试替代性能验收。
独立工作区中的开发改动继续保留，尚未发布正式版本。模拟器恢复原 Gboard，安装包逐项核对为本轮 E23。
本轮只使用专用模拟器，没有操作用户手机。证据索引为 `benchmarks/results/e23-evidence-manifest.json`，
阶段门槛为 `benchmarks/results/e23-acceptance-gate.json`；功能修复保留，性能推广和整体目标继续进行。

下一优先级：建立实际节奏可核对的快速触摸源，拆分系统准备与最新查询执行成本，再做性能改进；
保持候选质量、预算和学习语义，不以缩小搜索或挑选成功轮次换取较好数字。

# 证据清单的 Git 字节保留修复

E25 推送后，比较工作区与 Git 对象发现部分清单内容等价，但字节不同。
Windows Python 写出的 CRLF 被仓库 `text=auto eol=lf` 在提交时转换为 LF，
而依赖清单中固定的是原始文件 SHA-256，导致新检出后的依赖哈希校验失败。

## 修复范围

- 只为 `benchmarks/results/*-evidence-manifest.json` 设置 `-text`，按原始字节储存。
- 把 14 份受影响的已提交清单恢复为本地已有、其哈希被依赖记录引用的原始字节。
  JSON 解析后的对象全部相等；没有重算结果、改写历史指标或更改归档内容。
- 普通源码和其他 JSON 继续使用既有 LF 规则。
- 旧 release 标签保持原样；修复进入后续分支提交，不改 APK 或模型。

## 验证

1. 新增临时 Git 仓库测试：写入 CRLF 清单、执行实际 `git add`、读取 index blob 比较。
   修复前 2 项测试中 1 项失败，修复后 2 项通过。
2. 检查全部 14 份暂存清单逐字节等于原文件，记录原始/旧 Git 对象 SHA-256。
3. 验证现存清单里的 8,447 个 gzip 归档条目的压缩包哈希（有记录时）、解压原文哈希。
4. Python 工具全量 430 项执行，429 通过、1 项既有权限相关测试跳过；
   E23～E25 的依赖哈希与暂存 Git 对象一致。不将此修复计为输入算法改进。

审计结果：`benchmarks/results/evidence-manifest-byte-preservation.json`。
旧提交 `f26d32a` 保留问题现场；采用原始字节恢复，而不是修改历史依赖哈希以迎合转换后的文件。

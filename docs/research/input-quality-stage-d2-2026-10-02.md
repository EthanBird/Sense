# D2：取消过期的全拼搜索，而非只丢弃结果

## 结论

实现了真正进入解码搜索内部的协作取消。新字符到来、清空组合态或离开中文编辑时，过期任务在词格、混合分段、前缀候选及纠错检查点退出，不再完整算完才丢弃结果。正式模型的 125 条已知回归输出保持一致。

专用 API 37 模拟器中，新 APK 的三条追踪各记录 **14 次中途取消、1 次完成解码**；对应编辑框均最终得到“我喜欢北京”。这证明取消路径在系统 IME 中实际运行，不证明输入延迟已经达标。

## 实现与边界

- `DecodeWorkScope` 用线程局部探针包围同步 CPU 调用树；父作用域仍生效，异常退出恢复原作用域，不跨工作线程携带状态。
- 轻量 `DecodeSupersededException` 没有栈追踪及用户输入。中断中的前缀计算不写入缓存。
- `LatestOnlyTaskRunner.invalidate()` 使当前探针失效、移除待执行任务，工作线程仍可复用。
- Service 给全拼及已有替代布局工作加作用域；关闭组合态、切换输入类型时主动失效旧工作。修订号和模型代际的主线程发布检查继续保留。
- 系统追踪只记录固定名称 `Sense.Pinyin.decode` / `Sense.Pinyin.canceled`，不记录输入文本。取消标记嵌套于父解码区段；汇总脚本将其单独分类，避免把快速放弃误当成成功解码提速。
- 本阶段未调整分数、beam、候选上限、模型或词库。普通离线调用没有绑定取消探针，仍走同一排序逻辑。

Android 自定义追踪区段用法见[官方文档](https://developer.android.com/topic/performance/tracing/custom-events)。测量时显式启用应用追踪；生产代码没有逐键文本日志。

| LM 0.5 | 125 | 81 | 102 | 116 | 120 | 70 |

每条记录的 top5、目标名次、错误数及元数据全部相同；正式工厂测试另比较了活动取消作用域前后完整候选列表。模型与数据 SHA 未变，五个 core 源文件新增/修改，故 **旧开发冻结的源文件 pins 已不匹配当前源代码**。保留旧首次测试证据，不重新标榜为独立盲测。

新增回归覆盖搜索内部退出、前缀早停、异常/嵌套作用域恢复、跨线程隔离、取消计算不污染缓存，以及真实模型在更新请求到来后只发布最新结果。搜索检查点加入前，内部退出用例为红；加入后通过。

## 尚未完成

- 当前取消解决浪费在旧请求上的计算，不消除最新完整解码本身约数百毫秒的开销。
- 首次词库加载期间按空格的行为是另一条路径，D2 对照主动等待模型加载，没有覆盖；交由 D3 独立复现与修复。
- 仍需多句逐键延迟分布、短/长句交错输入、低内存生命周期，以及更完整的无障碍和横屏检查。

当前工作位于隔离开发分支，尚未发布 release。

# ADR 0020：v0.4.5 Skills 运行时、键盘手势与 Agent ABI

**状态：** Accepted（产品所有者于 2026-07-28 明确授权发布；确定性、Android 模拟器和
成品门禁仍须通过，真实 Provider Key 与固定实体设备绝对性能证据作为已知发布边界继续
保留，不记为通过）\
**日期：** 2026-07-27；发布决策：2026-07-28\
**目标版本：** Sense v0.4.5\
**上位决策：** [ADR 0019](0019-v0.4.4-open-agent-tools-and-complete-history.md)\
**工程规范：** [Skills 工程开发文档](../development/skills-engineering-plan-v1.0.md)

## 1. 背景

Sense 把工具、记忆和 Skills 作为 Agent 执行能力的第一优先级。Skill 不是一个临时
prompt 按钮，而是用户拥有、可修订、可绑定、可被 Agent 发现和读取的长期文档。输入法
又有比普通聊天界面更严格的交互边界：

- 普通按键、字符 flick、Delete 连续删除和 Space 长按 AI 不能互相抢占；
- 键盘高度不能因 Skill 选择而变化，也不使用弹窗；
- `:ime` 主线程不能等待目录扫描、文件锁或 `fsync`；
- 设置 Activity、IME 和私有 `:brain` 进程必须观察同一份完整数据；
- 用户按停止只能阻止尚未开始的副作用，不能伪装回滚已经越过线性化点的文件写入；
- 旧 revision、旧 catalog 和崩溃窗口中的完整数据不能被覆盖或删除。

## 2. 决策

### 2.1 Skill 是不可变文档 revision

每个 Skill 由稳定 `id` 和单调 `revision` 标识，包含：

- 简短名称；
- 暴露给默认 Agent 的单行 description；
- 完整 Markdown 指令；
- 仍受本地 Patch gate 约束的基础编辑意图；
- 是否为内置初始文档。

更新会写入新 revision。旧 revision 永不原地覆盖或删除。绑定、激活和当前 revision
引用位于不可变 catalog generation 中；原始 revision 与 catalog generation 都提供精确
历史读取。

持久化顺序为：

```text
跨进程 file lock
  → atomic replace HIGH_WATER，fsync store 根目录（先持久预留 generation）
  → 写临时 revision，fdatasync/fsync，atomic rename，fsync 父目录
  → 写临时 catalog，fsync，atomic rename，fsync catalogs
  → atomic replace CURRENT，fsync store 根目录
  → 返回成功
```

完整 catalog 是可恢复提交记录，`CURRENT` 是可见 generation，`HIGH_WATER` 是只增不减
的预留前沿。正常 `CURRENT == HIGH_WATER` 冷加载只按两个指针精确读取，不允许
`listFiles/sort` catalog 历史；正常 mutation 也由 HIGH_WATER 常数时间预留下一代。若
进程在 catalog 已完整落盘、CURRENT 尚未移动时终止，下次只探测 HIGH_WATER 指定的完整
catalog 并前滚；若仅完成预留，则保留 generation hole，继续使用旧 CURRENT，后续写入
跳过 hole。旧 store 缺少指针、指针损坏或互相矛盾时才执行一次全目录扫描并重建辅助
指针。扫描、恢复和冲突跳号均不得删除、覆盖或压缩任何 revision/catalog。写入和读取
使用相同编码字节上限，极限中文文档必须可全量重载。

### 2.2 绑定是语义键位 × 四方向

持久化槽位为 `keyCode + UP|RIGHT|DOWN|LEFT`。只允许当前键盘确实可渲染的字母、数字、
Enter 和稳定 action key；Space 永久属于 AI hold，Delete 永久属于连续删除。所有语义
键位四向合计上限为 208，catalog 还要通过最终编码大小门禁。

同一槽位只能绑定一个 Skill；一个 Skill 可以绑定多个槽位。全局同时只激活一个 Skill。
再次选择当前 Skill 会取消激活并恢复默认 Agent。

### 2.3 手势是显式状态机

非 Space/Delete 的可绑定键采用：

```text
IDLE → ARMED → PICKING → COMMIT | CANCEL
```

长按阈值前的移动继续交给原字符 tap/flick；进入 `PICKING` 后本次 pointer 归 Skill
选择器所有。方向解析必须 edge-aware，`Q-left`、`P-right` 和顶部键 `up` 均有可达路径；
若径向 chip 无法保持真实方位，则整体切换为带方向箭头的 shelf/fan，不允许逐个钳制后
把“左”画到源键右边。最终 `ACTION_UP` 坐标也参与解析，并使用方向迟滞避免对角线抖动。

选择器是键盘内 overlay，不改变高度。激活键覆盖动态极光，但长驻 active 动画必须由
只覆盖 owner key 的独立 child render layer 承担，不能每帧重绘承载背景、候选和全部
按键的父键盘 View。picker 是短暂交互，可以留在父层绘制。Android 硬件加速从 API 21
起可忽略 `invalidate(dirtyRect)` 的脏区参数，因此“请求一个小脏区”不能代替真实渲染
隔离。动画有帧率和分配预算；键盘隐藏、owner 不可见或系统关闭动画时必须撤销 frame
callback 并停止。

picker 松手时产生的是显式 `ACTIVATE|DEACTIVATE` selection intent，不是基于旧 projection
计算出的下一份 catalog。Repository 在跨进程 store lock 内把该意图与最新 catalog
线性化：激活仍要求同一槽位绑定同一 Skill，因而不会激活并发替换后的绑定；取消激活按
Skill identity 生效，因而不会因设置页同时移动/解绑原槽位而错误保留 active。并发正文
修订和其他槽位变更必须原样保留。

每次选择还携带仅用于 UI 关联的单调 request token。Aurora 先记录 provisional physical
owner，只有权威 catalog projection 与该 token 的期望 active 一致后才确认。physical
owner 由 surface、panel identity、稳定按键 signature 和重复序号描述，不依赖会因重绘
变化的 bounds、label 或 Shift 大小写。布局重建后只恢复同一物理 owner；重复语义键、
暂时隐藏的 owner、旧请求迟到失败都不得把极光迁移或清除到另一按键。

### 2.4 一次 Agent run 使用同一冻结 catalog

Space hold 不读磁盘。IME 只从已投影的内存 catalog 冻结：

- `skill_catalog_generation`；
- active Skill 的精确 `id@revision`、description 和完整正文；
- active Skill 的基础编辑意图。

Brain 必须读取请求指定的 immutable catalog generation，不能在 Binder 间隙切到“当前”
catalog。active 正文直接注入本次上下文；其他 Skills 只暴露 `id@revision + name +
description`，需要完整内容时调用 `skill_read`。

Brain START 使用本地 preflight：按 Android UTF-16 Parcel、Bundle entry/type metadata、
Message framing 估算，并为 64 条最大 discovery summary 预留兼容空间。Sense 产品上限为
448 KiB，低于 512 KiB 内部门禁至少 64 KiB；超限在 IME 进程返回 typed
`IPC_ENVELOPE_TOO_LARGE`，不得先尝试 Binder 后依赖 `TransactionTooLargeException`。
当前 summary 仍由 `:brain` 按冻结 generation 从不可变 catalog 读取，不在 Binder 中
重复传输。Android instrumentation 还必须以真实 `Bundle → Parcel.marshall → Bundle`
覆盖最大合法 snapshot、最大 active Skill、混合中文/代理对和 64 summary reserve。

Messenger 主线程只做有界解码、旧 identity 撤销和串行 admission 入队。Journal begin、
Provider/工具配置读取和 catalog generation 读取全部在 `sense-brain-admission` 专用 lane；
每个阻塞阶段后重新检查 exact `ActiveRun`。Service 销毁时先撤销 identity，已接收请求
保留 Begin/Cancelled，再由同一 lane 在全部 admission 之后关闭 transport 与 Journal，
不得主线程等待或与 close 竞态启动 Provider。

`skill_read` 使用精确 revision 和 `offset/max_chars` 分块，返回 `next_offset/eof`，不得
因为 16 KiB 工具结果上限而使合法的 64 KiB Skill 永远不可读取。

### 2.5 Agent 可以创建、更新和绑定 Skill

内置 `skill_manage` 是有类型工具，支持：

- `create`；
- `update`；
- `bind`；
- `unbind`；
- `unbind_skill`。

每次调用必须携带本次已知的 `expected_catalog_generation`。Settings、IME 或另一个
Agent 已经推进 generation 时，本次调用显式冲突，不得静默覆盖最新正文或槽位。成功
结果返回新 generation，后续同一 run 若继续修改必须使用新值。

工具 schema、prompt 中的可用性声明和执行 router 必须来自同一 provider capability。
OpenAI Responses、OpenAI-compatible Chat Completions 与官方 DeepSeek 路径不能出现
“prompt 要求调用但 wire 没有工具”的半实现。

工具设置除总开关外，分别提供 `skill_read` 和 `skill_manage` 开关。每次 run 在 admission
时冻结唯一 allow-list；总开关关闭时集合为空，任一 Skills 工具关闭时必须同时从 prompt
能力声明、Provider wire schema 和执行 router 消失，Brain 不得在冻结后无条件补回系统
工具。切换只影响后续 run 的能力，不删除 Skill、历史或既有工具结果。

### 2.6 取消的线性化语义

执行工具前，Brain 在 run lock 下再次验证 run/token。停止先发生时，不调用工具。
工具已经越过该检查并进入原子本地 mutation 时，停止不伪装回滚；mutation 可以完成，
完整记录工具结果，IME 通过 `CURRENT` 文件观察器刷新投影。历史 revision 使后续人工
恢复成为追加的新 revision，而不是破坏性回滚。

### 2.7 分层设置页是唯一人工配置入口

设置首页按 Provider、记忆（Soul）、工具、Skills、语音和关于分层。Skills 页负责创建、
编辑、绑定、解绑、查看历史和恢复为新 revision。草稿在分类切换、Skill 切换、旋转和
进程重建时不能静默丢失；被占用槽位必须显示现有绑定及替换影响。

现有 Skill 的文档草稿与键位 selector 必须分离：正文 revision 不拥有单个
`bindingSlot`，每个 Skill 另存用户最近明确选择的槽位。显式选择在绑定替换、解绑、
reconcile、保存、丢弃、Skill 切换和 Activity 恢复后保持；未显式选择才跟随 catalog
首选槽位。编辑正文不得隐式解绑同一 Skill 的其他槽位。

完整当前草稿的权威恢复源是应用私有原子 recovery snapshot；Bundle 只承载严格有界且能
逐 UTF-16 code unit 往返的小型 exact fallback。较大或尚未 durable 的当前草稿在
Activity 生命周期边界通过进程级串行 worker 和有界 durability barrier 交接；等待超时
只释放主线程，不能取消已经接受的 `fsync`。codec 必须保留未配对 surrogate，兼容旧格式，
并在损坏恢复文件上保留原始字节后再发布新 snapshot。达到产品上限后的整次编辑/粘贴应
原子拒绝并保留原草稿，不允许前缀截断。

这不建立第二套文件授权。应用私有 Skills 数据和用户通过 Android 已授予的目录都可以
被对应工具直接读写；开放能力不绕过 generation、结构校验和完整历史。

## 3. 明确延期

v0.4.5 不执行 Skill bundle 内的任意脚本、Dex、Python 或 shell。`scripts/`、
`references/`、`assets/` 与 Agent Skills 开放格式的导入/导出属于后续适配器；当前
Markdown 文档 ABI 保持可迁移，不把某一 Provider 或模型的 prompt 格式写入持久层。

多 active Skill 的组合、Skill 市场、签名分发和跨设备同步也不进入本版本。

## 4. 发布门禁

1. 65,536 个中文字符保存后由全新 Repository 逐字重载；
2. HIGH_WATER 预留及 revision/catalog/CURRENT 五个提交点故障注入；
3. 两个真实 JVM 进程竞争同一 store；
4. Settings/Agent/IME generation 交错，不允许静默覆盖；
5. active 正文、发现目录和 `skill_read` 来自同一 generation/revision；
6. 三类 Provider 均有请求 wire 与多轮工具回归；
7. `Q-left`、`P-right`、toolbar-up、最终 ACTION_UP、多指和 ACTION_CANCEL 回归；
8. Space AI、Delete repeat、字符 flick、编辑器 CAS 与 Agent 进度不回退；
9. IME pointer-up、onStartInputView、onWindowShown、Space hold 的 StrictMode 磁盘 I/O
   为零；FileObserver 丢失/目录失效后由合并后台 refresh 重建，并执行 read-watch-read；
10. Aurora 门禁分为两层，二者都不能互相替代：
    - API 36 x86_64 + SwiftShader CI 执行 3 个独立 30 秒窗口，验证结构隔离而非绝对
      设备性能。每个窗口中父键盘 `onDraw` 增量不超过 5；至少 2/3 窗口必须在每个
      5 秒 watchdog slice 中同时推进唯一 callback、overlay draw 与 FrameMetrics
      report，且 `|callback-draw| <= 1`、`|draw-report| <= 2`，避免只检查非零而放过
      内部僵尸循环；slice 末保持 `posted - executed = 1` 且零取消；ART 分配不超过
      1 KiB/overlay frame；FrameMetrics collector overflow 计入 dropped，dropped
      比例不超过 2%，并记录
      `DRAW/SYNC/COMMAND_ISSUE/SWAP_BUFFERS/GPU/DEADLINE/TOTAL` 分项。可以增加
      static/active 的 ABBA 相对基线，但不得把共享 runner 上的绝对 p95 或 active CPU
      当成硬件结论，也不得用任意降低后的固定帧数伪装吞吐通过。
    - active 清除后 1 秒内 reported/dropped frame 合计不超过 12、进程 CPU 不超过
      500 ms；这是每次都必须通过的停止门禁，不适用 2/3 quorum。
    - IME `onWindowHidden` 必须取消 Aurora callback，`onWindowShown` 可恢复；禁止以
      `hasWindowFocus()` 代替该生命周期，因为输入法窗口按平台设计可以是
      `FLAG_NOT_FOCUSABLE`。
    - 固定实体设备门禁必须显式 opt-in；运行前后绑定 exact target/test APK SHA-256，
      运行前固定动画配置，且运行前、每个 5 秒 slice 与结束时复验 fingerprint、刷新率
      和热状态上限；三个 30 秒窗口均须通过全部
      结构不变量、`TOTAL_DURATION p95 <= 32 ms`，并达到 33 ms 调度目标帧数的至少
      80%（约 24.2 fps）。普通 CI 中该测试必须明确 `SKIPPED`，不能由 SwiftShader
      自动降级阈值或替代这份绝对性能证据；
11. Settings 草稿恢复、历史恢复、Back、旋转和无障碍门禁；
12. 最大合法 Brain 请求真实 Parcel round-trip 小于 512 KiB，随后完整 Android 单测、
    Lint、M0–M6、APK、签名、权限和资源哈希通过。

以上 12 项仍是完整验收目标。产品所有者于 2026-07-28 明确要求立即发布 v0.4.5，并
接受真实 Provider Key、完整系统 IME 宿主交错和固定实体设备绝对性能证据延期补齐。
该发布决定不把缺失证据改写成通过，也不降低后续测试门槛；确定性回归、API 36 模拟器
结构门禁、APK、签名、权限和资产门禁仍必须由本次发布提交的 CI 全部通过。

## 5. 当前证据边界

截至 2026-07-28，当前分支已经实现不可变 revision/catalog、原子 selection intent、
physical owner/request token、显式 `skill_read`/`skill_manage` 设置开关、完整草稿恢复、
IME 后台 projection、448 KiB IPC preflight、分页读取和三类 Provider 工具循环。

当前源码声明的依赖无关测试清单为：`ai-protocol` 77、`brain-api` 37、`ai-brain` 120、
`ai-runtime` 151、`ime-service` 119、`ime-ui` 142、Settings 38。该数字表示当前测试
inventory，不自动等于 Android 发布通过。`ai-runtime` 的 151 项中有 4 项显式 opt-in
真实网络探针；本环境未提供临时 Key，因此真实 Key **0 项通过、4 项明确 SKIPPED**。

AndroidTest 源码为 `ai-runtime` 1 项、`ime-service` 2 项、`ime-ui` 13 项、Settings
2 项。CI #61 的 API 36 x86_64 模拟器已实际报告 **18 项：17 项通过，固定实体设备
绝对性能门禁 1 项以 JUnit Assumption 明确跳过**；Settings 两项也实际执行。三段
30 秒 Aurora 结构样本均通过 callback/draw/report liveness、父键盘零重绘、分配预算和
停止门禁。完整 Gradle、Lint、M0–M6、APK、签名、权限 typed value 和资源哈希在同一
候选上通过；v0.4.5 版本提交仍须重跑同一流水线。

当前仍没有同一候选提交的固定实体设备 `TOTAL_DURATION p95 <= 32 ms` 证据，不能把
SwiftShader 耗时记为设备性能通过；真实 Provider Key 通过数也仍为 0。它们是本次明确
披露且由产品所有者接受的发布边界，而不是测试成功。

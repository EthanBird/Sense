# ADR 0023：v0.4.5.beta.5 解码质量、个性化与候选一致性

- 状态：Accepted
- 日期：2026-07-30
- 版本：v0.4.5.beta.5
- 相关决策：ADR 0004、ADR 0005、ADR 0006、ADR 0007、ADR 0022

## 背景

此前全拼、动态分词、简拼、混拼、前缀、英文、纠错和用户词各自排序，再通过提前返回、
固定插入位置或局部截断合并。结果是同一个候选在不同来源之间缺少可比较的分数，exact
命中会遮蔽合法分词与纠错路径，渐进前缀也可能把整句候选推到很深的位置。

异步解码还存在另一类一致性问题：新 revision 计算期间清空旧候选会引发候选栏跳动，
继续显示旧候选又可能让旧索引被点击提交。个性化只有累计次数，缺少选择强度、时间衰减
和误选反馈，也难以与系统词典分数稳定融合。

本决策把上述问题收敛为四个边界：

1. core-input 负责有界召回、统一排序、上下文和个性化分数；
2. ime-service 负责异步 revision、编辑器上下文、学习反馈窗口和持久化；
3. ime-ui 负责 pending 的稳定几何与交互冻结；
4. 版本化回放与 Host 性能预算负责阻断质量和耗时回退。

## 决策

### 1. 所有候选进入统一 `CandidateRanker` 分数域

`PinyinDecoder` 先收集规范 exact、动态组合、hybrid、initials、prefix 和 spelling-graph
纠错，再执行一次全局排序；exact 命中不再提前结束召回。`AdaptivePinyinDecoder` 把
用户候选换算到相同分数域，`MixedCandidateRanker` 也把中文与英文候选交给同一
`CandidateRanker`，移除固定英文槽位。

最终分数为候选来源分数加来源先验。当前常量为：

| 来源 | 先验 |
|---|---:|
| 当前输入存在规范 exact 时的 exact 集合 | `+8.00` |
| 无 exact、但存在规范多段组合时的组合集合 | `+6.00` |
| 其他 exact | `+1.20` |
| 其他组合 | `+0.55` |
| 用户词 | `+0.45` |
| hybrid | `+0.55` |
| initials | `+0.10` |
| 英文 exact | `+0.40` |
| 无规范 exact/组合时的 correction | `-0.25` |
| 已有规范 exact 时的 correction | `-13.00` |
| 无 exact、已有规范组合时的 correction | `-8.00` |
| prefix | `-0.75` |
| 英文 prefix | `-0.90` |

`+8/+6` 是 Frost 与英文 log-like 分数域上的有界规范输入保护，不代表独立概率，也
不建立不可跨越的固定槽位。已有 exact 时 correction 使用 `-13` guard；没有 exact、
但存在规范组合时使用 `-8`；原输入本身缺少规范路径时仍使用 `-0.25`，让纠错结果
正常参与竞争。
中英文合并阶段还会给“单拼音首字母 → 单个汉字”的 `BASE_PREFIX` 加 `+4.5` 双语
证据校准，使 `w → 我` 这类明确中文模式信号不被宽泛英文补全淹没；它同样只是分数
特征，不预留候选位置。

候选按文本去重，保留较高总分及可用的规范拼音元数据；稳定次序依次比较总分、来源
优先级、Unicode code point 长度和文本。英文 exact、复数/词形及词法补全仍由
`EnglishLexicon` 决定召回证据，最终位置由统一分数决定。

词典候选的基础分为 `ln(unsignedWeight + 1)`，legacy fallback tier 另扣 `1.0`。
动态 prefix 每缺少一个字母扣 `0.08`；简拼文本 code-point 数与查询长度相等时加
`3.0`，恰好四字时改为加 `10.0`。这些是候选自身证据，之后才叠加上表来源先验。

### 2. 纠错使用有界加权拼写图

`PinyinSpellingGraph` 在音节清单上构造逐音节边，而非对整段输入执行
`26 × n` 字符枚举。图同时保留规范路径与以下编辑：

| 编辑 | 代价 |
|---|---:|
| `n/l`、`f/h` 以及 `zh/ch/sh`、`ng` 相关模糊音 | `0.25` |
| 重复键 | `0.30` |
| QWERTY 邻键替换 | `0.35` |
| 相邻字符换位 | `0.45` |
| 普通字符替换 | `0.90` |
| 普通插入或删除 | `1.00` |

Graph API 默认最多保留 24 条完整路径；生产 `PinyinDecoder` 通过
`CorrectionSearchBudget.PRODUCTION` 根据 canonical 证据和输出上限选择 24 或 48 条，
无 canonical 时始终请求 48 条。总代价上限为 `1.05`，每个输入偏移最多 64 条边。
完整可逆 composition 的规范化 ASCII 字母总长度（已选片段与待解码尾部合计）上限为
96，通用图单元长度上限为 24。撇号形成强制音节接缝，
因此 `xi'an` 保留两个音节的路径。纠错候选分数扣除 `4 × editCost`。

生产纠错预算为：

| 项目 | 无 canonical（任意 limit） | 有 canonical，`outputLimit < 64` | 有 canonical，`outputLimit >= 64` |
|---|---:|---:|---:|
| spelling paths | 48 | 24 | 48 |
| exact candidates / path | 48 | 48 | 48 |
| composed paths / probes | 4 | 1 | 3 |
| composed candidates / path | 24 | 24 | 24 |
| segment candidates / key | 8 | 8 | 8 |
| segment beam | 32 | 32 | 32 |

资源策略与词库记录数解耦：生产和测试运行同一搜索实现；需要窄预算的测试通过
`CorrectionSearchBudget` 显式注入。通用 `PinyinSpellingGraph` 可接收最长 24 的
图单元，而 `PinyinDecoder` 从任意 SPLX 中只把长度不超过 6、且存在单音节候选
（`initialsLength == 1`）的规范记录加入纠错 inventory。
compact canonical 档位降低小结果集的重复搜索量；无 canonical 的输入保留完整
48/4 召回，生产上限请求也继续使用 48/3。

为避免大量低代价前部歧义挤掉长句尾部错误，图在每个输入偏移对每种 cost tier
优先保留至多 8 条边，再补齐到总计 64 条；path beam 达到目标宽度 4 倍时裁剪。
同一 canonical 和 `0.001` 量化 cost 最多保留 4 种分段，每个 beam 最多保留 4 条
零编辑路径，每个 `firstEditOffset × costTier` 优先保留至多 12 条，并让更靠后的
首次编辑位置先进入保留集。`firstEditOffset` 是替换、换位、插入或删除发生的真实
绝对字符偏移，不是该音节边起点；同成本重复键路径保留更靠后的重复字符。生产音节表
和 48 路预算以 `nihaoshijiee → ni/hao/shi/jie → 你好世界` 固定该契约。

corrected exact 从全部保留的 spelling paths 读取。组合 probe 先按“存在 exact record”
优先，再按便宜的词格估算分减 `4 × editCost` 排序并按 canonical 去重；随后优先纳入
至多 2 条单字母尾部增删路径，并尝试纳入首次编辑位置距离最靠后位置不超过 1 的路径，
再用排序结果按档位补齐至 4、1 或 3 个名额。`PinyinSpellingPath.syllableEnds` 会传入
纠错词格，词格边只能落在对应音节端点，候选 initials 数也必须等于所覆盖的音节数，
避免纠错路径被重新解释为另一种分段。

### 3. 动态分词使用词格与有界 beam

动态组合把输入位置作为词格节点，把词典中长度不超过 24 的 exact 子串作为边。除
`a/e/o` 外，单字母记录不参与正常组合扩展，避免 `fu + n` 一类伪音节改变合法性判断。
组合召回与 canonical correction guard 复用同一 edge eligibility：边必须满足上述
单字母规则，并且不得跨越撇号声明的 forced joint。

搜索预算随请求上限分两档：

| 项目 | 小请求 | 候选上限至少 64 |
|---|---:|---:|
| 每个词格边读取候选 | 8 | 16 |
| beam 宽度 | `max(24, limit)` | 96 |

beam 达到宽度的 4 倍时批量裁剪，并以“文本、片段数、末片段是否单字”为状态身份
去重。路径累计词典分数和字符 bigram；两个多字词之间的边界 bigram 乘 `0.04`，其余
边界使用完整 bigram。最终组合分数为：

```text
(pathScore - 0.65 × (segments - 1)) / segments
```

从编辑器左侧进入首字符的 bigram 分数限制在 `[-3, +3]`，避免单个上下文边压过整条
词格路径。

其他召回路径同样有明确预算：总输出最多 255 项；initials 查询至少 2 个字母；hybrid
查询至少 3 个字母，最多扫描 128 条 namespaced record、每条读取 16 项，工作集超过
`max(3 × limit, 64)` 时保留 `max(2 × limit, 32)`。动态 prefix 的通用词典
lower-bound 扫描最多 96 条 record、每条读取 2 项；对应首字母的单音节 inventory
另行遍历，统计 prefix 则直接读取预编译 namespace。存在规范 exact 时停止 prefix
补全，但 exact 不会终止组合、hybrid、initials 和纠错召回。

输入先转为小写并只保留 ASCII 字母；96 上限约束该规范化 query，撇号只记录 forced
joint。存在 forced joint 时跳过整段 exact、hybrid、initials 和 prefix，组合词格与
spelling graph 均禁止任何边跨过该 joint。

渐进式前缀选择通过 `ProgressivePrefixProbeDecoder` 调用轻量 probe。canonical exact、
组合、hybrid、initials 和 prefix 补全仍参与，但每个前缀不再重复运行 spelling
correction graph；`wholeCandidates` 仍走 `decode` / `decodeAfter` 的完整路径并保留
纠错召回。

### 4. 上下文统一取最近一个 Unicode code point

一次新 composition 开始时，ime-service 在主线程读取光标前最多 2 个 UTF-16 code
unit（足以容纳一个代理对），随
`CandidateDecodeRequest` 的不可变快照送入后台解码。渐进选择已经产生
`PinyinComposition.acceptedText` 时，以完整 accepted text 为更新、更近的上下文；
否则使用捕获的编辑器左侧文本。两种情况都通过 `codePointBefore(length)` 取最后一个
Unicode code point，再调用 `decodeAfter`。

因此多字符 accepted segment（例如“中华”）使用“华”而非丢弃整段上下文，代理对
字符也按 code point 处理。当前语言模型仍是 65,536 条字符 bigram，而非任意长度语言
模型；完整 `acceptedText` 继续作为渐进 composition 的上下文边界，编辑器侧则只冻结
当前模型需要的最近 code point。密码 variation 不读取临时上下文；
`IME_FLAG_NO_PERSONALIZED_LEARNING` 只关闭持久学习，不影响普通非密码字段的瞬时
bigram 解码。

### 5. 个性化采用正负证据、衰减和 SQLite v3

学习事件区分三种正反馈：

- 默认首选提交：`0.18`；
- 显式选择：`1.75 + min(0.4 × ln(rank + 1), 1.25)`；
- 渐进前缀选择：`0.65 + min(0.15 × ln(rank + 1), 0.45)`。

`rank` 为零基候选位次，并限制到 255。正反馈半衰期为 14 天，负反馈半衰期为 7 天；
历史正证据保留 `0.25` 的长期频次底座。频次奖励上限 `1.7`，最近事件奖励上限 `3.0`。
负证据按 `1.15` 系数形成惩罚，最终个性化调整限制在 `[-4.5, +4.5]`，因此误选反馈
既可抵消用户词奖励，也可直接降低同文本基础候选的分数。快速删除增加 `3.5` 负证据，
立即替换增加 `4.0`，手工降权增加 `2.0`；正负累计证据各限制到 10,000。

`PersonalizationFeedbackWindow` 只保留最近一次学习提交，窗口为 3 秒，并核对提交区间
与当前光标/选区。渐进选择先进入 composition 内的待提交队列；完整上屏成功后才写入
学习记录，composition 内回退则丢弃对应待提交事件。用户词与已有基础候选重合时补偿
来源先验；只存在于用户词典的候选以当前基础首分减 `2.25` 作为锚点。简拼用户词另扣
`0.2` 歧义代价。

热路径继续查询 `MemoryUserLexicon`。SQLite 仅承担串行异步持久化，并启用 WAL。
内存索引最多保留 10,000 条记录、每个完整拼音最多 64 条；超出预算时淘汰当前
个性化调整最弱且更旧的记录，并通过同一持久化队列删除。
每条记录默认最多保留 16 个 alias；每个 initials/alias 非 exact 查询桶最多索引
128 条记录，lookup 使用有界 top-K heap。非 exact 桶裁剪只移除索引映射，不删除
底层记录，因此完整拼音 exact 召回和已经写入的负反馈记录继续保留。
数据库版本升级到 3，新增：

- `positive_evidence`
- `negative_evidence`
- `last_positive_evidence`
- `last_negative_at_ms`

v2 升级时以 `use_count` 初始化正证据，保留既有短语、别名、创建时间和最近使用时间。
删除用户词通过同一串行队列写入 durable journal。数据库 open/migration/read 完成后才
把资源所有权交给 writer；load、writer 创建或内存快照构建任一阶段失败，当前
SQLite/writer owner 都会同步关闭，并把 close 异常作为原始异常的 suppressed 信息保留。

### 6. pending 候选采用“保留几何、冻结交互”契约

新 composition revision 开始解码时，`CandidateDecodeSession` 保留上一批
`ProgressiveCandidateSnapshot` 供视觉连续性使用，同时发布 `pending=true` 和
`decoding=null`。旧 revision、同 revision 但 composition 内容不同、remaining pinyin
不一致的完成结果均被丢弃；`select` 在 pending 或 composition 不匹配时不产生选择。

`CandidatePanel.publish(values = null)` 把这次发布解释为 pending：保留旧候选测量与几何，
设置 `candidatesReady=false`，清理 drag/settle/scroll 状态，停用候选点击、展开、翻页和
拖动命中。renderer 在 pending/ready 间保持相同主题文本颜色，readiness 只作为交互
契约，避免每次按键都因候选文字调色产生整栏频闪。readiness 改变或候选内容批次替换
前，`CandidatePointerFence` 会取消所有候选相关活动指针；因此旧批次 `DOWN` 即使跨过
新批次发布，也不会在 `UP` 时按冻结的旧 source index 提交。新快照完成后，候选、
revision 和可交互状态原子切换；composition 标题在 pending/ready 两种状态使用同一
几何，避免垂直跳动。

展示快照顺序为：

1. 前 12 个整词候选；若首候选是英文，则整词头部为 3 个；
2. 4 个代表性渐进前缀，并优先覆盖不同 `consumedPinyin` 路径；
3. 其余整词候选；
4. 其余渐进前缀。

存在规范单汉字 exact 的单音节输入时，前缀总量限制为 4。core 整词和渐进前缀上限
各为 255，service 展示快照上限为 510。Han 判断与字符计数按 Unicode code point 和
`UnicodeScript.HAN` 执行，Frost 中补充平面字可进入渐进候选并作为单字学习。

英文 composing 的 type/backspace 也采用两阶段宿主边界：先冻结
`EnglishInputSession`、revision、editor session 与 `InputConnection` 身份，宿主
`setComposingText` 成功且同步回调未改变这些身份后，才推进本地 session 和候选快照。

### 6.1 Frost 与个性化数据异步装载

`InputMethodService.onCreate` 先装配 `FakeDecoder`、空英文词表、fallback 音节表和
内存用户词典，使 IME 生命周期与 35 MB Frost 扫描、bigram/英文资产读取及 SQLite v3
迁移分离。专用单线程 `sense-decoder-loader` 在后台构建完整的不可变
`AdaptivePinyinDecoder`；候选工作线程每个请求都读取当前 `@Volatile decoder`，完整
实例就绪后由主线程一次性热切换。

热切换会重建并恢复正在输入的英文 composition；若中文 composition 仍有 remaining
pinyin，则通过 `forceDecode` 重新进入 pending 并重新解码，避免沿用 bootstrap
结果。生产解码器就绪前暂停个性化写入，切换后再按当前编辑器持久化策略启用学习。
单项资产或持久词典加载异常会记录错误并使用对应的本地 fallback；服务销毁时关闭
loader，迟到结果也不会安装到已销毁实例。

### 7. M3 质量回放成为版本化阻断门禁

`benchmarks/replay/m3-sentences.tsv` 包含 120 条确定性用例：全拼 20、长句 20、姓名 15、
口语 15、技术词 15、单处拼写错误 12、简拼 12、混拼 11；其中 4 条携带上下文，2 条
携带等价 alias。词频桶为 head 74、mid 41、tail 5。该集合用于版本回归，不作为真实
用户总体准确率估计。

2026-07-30 生成的 `benchmarks/results/m3-sentence.json` 使用
`pinyin_lexicon.bin` SHA-256
`71258c3d1b4cade8693a13564ead0217a7e92068bbe554ecc806ae0f3a08e800`。

### 8. 生产性能预算同时约束质量回放与高频核心路径

M3 的生产上限预算为：

- 非 typo、limit 255：p95 `≤ 35 ms`，p99 `≤ 60 ms`；
- typo、limit 255：p95 `≤ 40 ms`，p99 `≤ 70 ms`；
- contextual p95 `≤ baseline p95 × 1.35 + 0.5 ms`。

M4 使用 20 个 batch 的 nearest-rank p95，因此 p95 取第二差 batch，而不是 7 个
batch 时的单次最大值。每个 batch 的 lookup 数按比例缩小，总 lookup 预算与原门禁
完全一致。2026-07-30 的 `benchmarks/results/m4-core.json` 记录：

| 路径 | 实测 p95 | 预算 |
|---|---:|---:|

纠错图后仍保留了完整的有界前缀结果集。`RankedCandidateDecoder` 把已经过滤、去重、
按分数排序且满足 limit 的生产解码器结果标记为可复用；空个性化查询不再重复进入
CandidateRanker。前缀 group 在构建时一次性保存 whole/decode rank，排序比较阶段不再
创建 substring、Pair 或执行 Map 查询；泛型 `InputDecoder` 仍走完整归一化路径。
本地发布门禁把 M4 与 M3 一样安排在持续负载型 M0–M2 之前，避免宿主热降频污染
绝对延迟判断，工作量和阈值均保持不变。

## 与 ADR 0022 的关系

ADR 0022 定义 GPL-3.0-only、Rime Frost 固定 revision、源文件哈希、canonical IR、
权重校准、fixture 隔离和离线逐字节重建。本 ADR 使用该生产产物并规定运行时的召回、
排序、学习、展示和质量门禁；它既不替代 ADR 0022，也不改变其 source/artifact 边界。

当前 Frost 产物包含 524,851 个 exact key、610,298 个 exact candidate、608,314 个
唯一 exact 文本，SPLX v3 为 35,069,585 bytes。字符 bigram 仍由词典派生；本 ADR 的
上下文改善不等同于接入独立语料语言模型。

## 结果与取舍

- exact、组合、简拼、混拼、英文、纠错和用户词可以在一处审计分数与稳定次序；
- spelling graph、词格、beam、前缀扫描和候选数量均有硬上限，35 MB Frost 词库不会
  让搜索空间按词条数量无界扩张；
- pending 期间保留候选几何，消除空列表到新列表的跳动，同时旧候选保持非交互；
- 个性化可以快速强化显式选择，也能通过删除/替换形成有界负调整，直接降低误选候选；
- Frost、bigram、英文词表和 SQLite 迁移离开 IME 主线程，并以完整实例原子热切换；
- `+8/+6` 规范路径先验与 `-13/-8/-0.25` 分级 correction guard 是当前
  Frost/英文分数校准，后续若所有来源改用同一统计标定，应通过新 ADR 调整并重跑
  120 条回放；
- 120 条回放和 Host 耗时用于确定性回归；真实用户准确率、设备帧时与输入端到端延迟
  由独立采样补充。

## 门禁

1. `CandidateRankerTest`、`PinyinSpellingGraphTest`、`PinyinDecoderTest`、
   `EnglishLexiconTest` 和 `AdaptivePinyinDecoderTest`覆盖统一排序、纠错、词格、
   上下文和个性化边界；
2. `CandidateDecodeSessionTest`、`ProgressiveCandidateSnapshotTest` 和
   `CandidatePanelTest`、`KeyboardInteractionControllerTest` 覆盖 pending revision、
   代表性前缀、全局索引、触控屏障和交互冻结；
3. `PersonalizationFeedbackWindowTest` 与 service contract 测试覆盖快速删除、
   替换、数据库迁移字段和持久化边界；
4. `m3SentenceBenchmark` 必须生成 120 条质量、分桶、p50/p95/p99 和门禁结果；
5. `m4CoreBenchmark` 必须通过 initials、渐进解码、生产候选上限和词格组合预算；
6. `m5MixedInputBenchmark` 必须通过中英排序、Frost hybrid、用户 alias 与三条 p95
   预算；
7. `offline_verify` 必须继续通过 ADR 0022 的 Frost source-to-artifact 重建与许可门禁。
